# Customer Churn

Учебный ML-проект: сервис поддержки удержания клиентов телеком-компании.

## Задача

По характеристикам клиента оценить риск оттока. В будущей версии сервиса
пользователь загружает CSV, задаёт количество клиентов для кампании и получает
список с наибольшим прогнозируемым риском.

В исходных данных целевая переменная — `Churn`: `Yes` означает отток,
`No` — его отсутствие. `customerID` — идентификатор, его не будем использовать
как признак модели.

## Что уже работает

- Загрузка фиксированной версии датасета из репозитория IBM.
- Проверка размеров таблицы, целевой переменной, пустых значений и повторов ID.
- Воспроизводимое разбиение train/validation/test примерно 60/20/20.
- Сравнение DummyClassifier, логистической регрессии, случайного леса и бустинга.
- Оценка на validation при пороге 0.5; финальный test пока не оценивался.
- Анализ ошибок по договору и стажу; эксперимент с пропусками TotalCharges.
- Подбор небольшого набора настроек через повторную стратифицированную CV на train.
- Precision@K, recall@K и lift@K на validation при K=50, 100, 200, 500.
- Интерфейс пока не реализован.

## Первый запуск

Нужен Python 3.12. Версии зависимостей зафиксированы в `requirements.txt`.
Команды выполняются из папки проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python scripts/download_data.py
python scripts/inspect_data.py
python scripts/train_baseline.py --compare-models
```

Для загрузки нужен интернет. Повторный запуск использует уже скачанный файл.

## Обучение и результаты

`train_baseline.py` использует `random_state=42` и стратификацию по `Churn`.
Заполнение пропусков и кодирование категорий обучаются на train внутри pipeline.
Для логистической регрессии дополнительно применяется StandardScaler.
`customerID` и `Churn` исключены из входных признаков.

С флагом `--compare-models` обучаются все четыре варианта. Без флага сохраняется
первоначальный эксперимент с DummyClassifier и логистической регрессией.

После запуска создаются:

- `reports/comparison.json` — метрики четырёх моделей на validation, параметры,
  фактические глубины деревьев, версии библиотек и SHA-256 исходного CSV.
- `reports/baseline.json` — первоначальный эксперимент с двумя моделями.
- `artifacts/splits.json` — ID клиентов в каждой части для последующих экспериментов.
- `artifacts/<название_модели>.joblib` — обученные модели и их преобразования.

Существующий `splits.json` проверяется перед обучением: скрипт останавливается,
если данные или состав частей изменились. Это защищает сравнение от смены выборки.

Артефакты исключены из Git и воспроизводятся командой обучения.
Методика и результаты: [первые модели](reports/README.md),
[сравнение четырёх вариантов](reports/comparison.md).

Анализ ошибок и проверка заполнения пропусков новых клиентов:

```bash
python scripts/analyze_errors.py
```

Отдельный [отчёт эксперимента](reports/error_analysis.md) содержит статистики
train и результаты на validation. Основной pipeline пока сохраняет медиану;
небольшое изменение AP на одном разбиении не подтверждает устойчивого улучшения.

Подбор настроек с полным pipeline внутри каждого фолда:

```bash
python scripts/tune_models.py
```

Сравниваются 12 конфигураций на одинаковых пяти фолдах train с двумя повторениями.
В каждой семье выбирается вариант с наибольшей средней AP по CV, затем он
обучается на всём train и оценивается на неизменной validation. Результаты:
[методика и сравнение](reports/tuning.md), [полный отчёт](reports/tuning.json).
CV-разбиения сохраняются в `artifacts/cv_splits.json`, выбранные pipeline —
в `artifacts/cv_selected_<название_модели>.joblib`. Они не заменяют исходные модели.

Оценка списков клиентов для кампании:

```bash
python scripts/evaluate_campaign.py
```

Скрипт читает настройки из `reports/tuning.json`, проверяет данные и протокол,
заново обучает исходные и выбранные конфигурации на train и ранжирует validation.
Прежние глобальные метрики должны воспроизвестись. Риск сортируется по убыванию;
при равенстве используется ID по возрастанию. `Churn` участвует только в оценке.
Сравнение с математическим ожиданием случайного отбора и результаты:
[отчёт кампании](reports/campaign.md), [полные метрики](reports/campaign.json).
Локальные CSV с рангом, ID и риском сохраняются в `artifacts/rankings/`.
Для выбранного по CV леса и логистической регрессии precision@100=78%,
recall@100=20.86%; ожидаемая precision случайного отбора — 26.54%.
Это ретроспективная оценка выявления оттока, не эффект удержания.

## Проверки

```bash
python -m unittest discover -s tests -v
```

Проверяются отсутствие пересечений между частями данных, повторяемость разбиения,
обучение преобразований только на train, обработка неизвестных категорий
и отклонение повторных ID. Проверки CV также подтверждают отсутствие внешних
validation/test во фолдах и обучение преобразований на обучающей части каждого фолда.
Для списков клиентов проверяются метрики, обработка равных рисков, независимость
от порядка входных строк, некорректные K/ID/риски и случаи с единственным классом.

## Следующие этапы

1. Расширить поиск сочетаний гиперпараметров через RandomizedSearchCV на train.
2. Сопоставить кандидатов на validation по AP и качеству первых K клиентов;
   зафиксировать модель и режим отбора. При фиксированном K порог 0.5 не нужен.
3. После выбора подхода один раз провести финальную оценку на test и разобрать ошибки.
4. Добавить простое демо с выгрузкой списка клиентов.

## Ограничения

Используется учебный датасет IBM Telco Customer Churn, а не банковские данные.
Прогноз риска не показывает, кому поможет предложение об удержании.
Без данных о кампаниях нельзя подтвердить эффективность вмешательства или экономию.
Проект не обещает прогноз на произвольный будущий период: для этого нужны
определённый горизонт и данные с временными метками.

Источник и зафиксированная версия: [data/README.md](data/README.md).
